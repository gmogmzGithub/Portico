# Snowflake Setup

Configure the bundled Snowflake MCP integration without exposing credentials or existing connection-file values to the model.

Do not require `server:snowflake` before setup; its required files may not exist yet.

## Required First Actions

For every setup, repair, or general request such as "Help me connect Snowflake":

1. First call `agent_vm_set_chat_workspace` with:
   - `host_path="~/.snowflake"`
   - `timeout_seconds=3600`
   - this exact `preamble`:

```markdown
Snowflake keeps its local connection files in `~/.snowflake`. Allowing access lets Portico check whether Snowflake is already configured and create or update the files needed to connect it. Your token is handled separately through a secure masked prompt.
```

2. Stop if consent is denied, cancelled, or times out.
3. Call `agent_vm_create`.
4. Run `scripts/snowflake_inspect.py` with `--output-dir /work` through `agent_vm_execute_skill_script`.
5. Infer progress from its enums before asking the user anything.

An `empty` result means the user is at the very beginning. Do not ask `Which step are you at?`; proceed directly to the secure PAT flow.

The user's own request is the approval for files this app owns: when they asked to set up, fix, reconnect, or re-token Snowflake ("set up snowflake", "it didn't work, try again", "my token is broken") and `connections.toml` is missing, a secure stub, or generated by Portico (`connections.generated: true`), run the needed operation with `--replace-existing` without asking a separate replacement question. A hand-written connection file (`generated: false` and not a stub) is the user's own work: ask one plain-language question before replacing it, no matter how clear the request. Also ask when intent is genuinely ambiguous — for example, the user asked something unrelated and inspection found an unusable file. `mcp_config.yaml` is different: never replace it without explicitly asking first when that specific file is unusable.

In every question, preamble, or status message you produce for the user, use plain language only: say "your saved Snowflake connection" or "your Snowflake settings", never internal terms like "Trust Kit", "secure stub", "protected connection file", or file-classification enums. Internal terms in this document are for your reasoning, not for user-facing text.

## Non-Negotiable Secret Boundary

`scripts/snowflake_inspect.py` is the only permitted way to inspect `/work/connections.toml` or `/work/mcp_config.yaml`. Never use file-read tools, shell commands, Python snippets, screenshots, links, or file display to expose either file. Never request, print, echo, summarize, or return any value from an existing connection file.

The inspector returns only state enums, safe issue codes, and allowlisted missing field names. Treat all other access paths as prohibited even if the user asks for a diagnosis.

Never ask for a PAT, API key, password, or client secret in chat. Use `agent_vm_request_sensitive_information`, pass only its temporary file path to `scripts/snowflake_setup.py`, and never read that file. The setup script's output is intentionally value-free.

## State Decisions

Explicit user intent overrides `overall_state`: when the user says the connection or token is broken, expired, or that they want to provide a new token, go straight to the Secure PAT flow — use `--operation rotate-token` only when `connections.state` is `complete`; when it is `secure_stub` or `connections.toml` is otherwise unusable, collect the PAT and LDAP username and use `--operation connections --replace-existing` (their request is the approval) — and do not enable first. A rotation must produce a fresh full connection file: while the host file is a secure stub, Portico keeps serving the previously imported secret bytes, so keeping the stub leaves the old token in effect.

`connections.issue_code: "legacy_pat_credential"` means an older generated file that stores the token under `password` while naming the PAT authenticator — a shape the Snowflake connector cannot sign in with. It is only reported for files Portico generated, and enabling migrates them automatically: treat the file as usable without asking anything, and when the user asked for a repair with a fresh token, `--operation rotate-token` also rewrites it to the current shape.

The issue codes `pat_credential_key_mismatch`, `ambiguous_credentials`, and `unsupported_credential_shape` mean a hand-written or hand-edited connection file whose credential layout the connector cannot sign in with. Treat the file as unusable and repair it with a fresh token through the replace flow — remembering that hand-written files get one plain-language question before replacement.

Absent such explicit intent, use `overall_state` exactly:

- `empty`: collect a PAT and the user's LDAP username; run setup with `--operation all`.
- `candidate_ready`: enable Snowflake immediately. If it becomes tool-ready, activate it without collecting a PAT.
- `connection_only`: preserve `connections.toml`; create only the default Trust-Kit MCP config with `--operation mcp-config`.
- `config_only`: preserve `mcp_config.yaml`; collect the PAT and LDAP username, then use `--operation connections`.
- `ambiguous`: preserve both files. When the user's request already expresses setup/repair intent, replace only the unusable target with `--replace-existing` (hand-written connection files still get the one plain-language question first); otherwise ask one targeted plain-language question about only the unusable file.

If authentication fails and `connections.state` was `complete`, collect a fresh PAT and use `--operation rotate-token`; the script preserves all other connection fields internally. If a `secure_stub` no longer has usable secure storage, recollect the PAT and LDAP username, then replace only `connections.toml` after the user approves. Never attempt to read Keychain or secure runtime material.

`mcp_assistant_toggle_integration` reports that unavailable saved-secret state as `errorCode: "SAVED_SECRET_UNAVAILABLE"` with `configurationIssue: "saved_secret_unavailable"`. Treat either field as authoritative: do not retry the toggle and do not open generic guided setup. Immediately continue the Secure PAT flow, collect a fresh PAT plus the LDAP username, run `--operation connections --replace-existing`, validate the newly written connection, and then enable exactly once more. The user's setup or repair request is already approval to replace an Portico secure placeholder.

Preserve valid custom MCP configuration. New MCP configuration defaults to the Trust-Kit config — the connection does not work without it. Offer the read-only mode (`--mode read-only`) or further customization only after Snowflake is connected and tool-ready, and only if the user asks; guide any customization from this skill's documentation.

## Non-Secret Inputs and Script Operations

Collect only the user's missing LDAP username in chat, plus the token's role when the user granted the token a single role other than `PUBLIC` (role names are not secrets; pass a non-default role as `--role <ROLE>`). The `role` written to `connections.toml` must match the token's role restriction or Snowflake rejects the sign-in. Every other connection value is fixed and defaulted by the script: account `PORTICOORG-PORTICO`, role `PUBLIC` by default, authenticator `PROGRAMMATIC_ACCESS_TOKEN`, and `<none selected>` for warehouse, database, and schema. The username is not a credential; never source it by reading an existing connection file.

Call `scripts/snowflake_setup.py` with `--output-dir /work`, the required `--operation`, and only the arguments that operation needs:

- `all` or `connections`: token file path plus `--user` (LDAP username), and `--role <ROLE>` when the token was granted a single role other than `PUBLIC`.
- `mcp-config`: no extra arguments; do not request a PAT. It writes the default Trust-Kit configuration.
- `rotate-token`: token file path only. It fails with `connections_file_stub` when `connections.toml` is a secure stub — use `--operation connections --replace-existing` instead.
- `validate`: no extra arguments; do not request a PAT. It signs in to Snowflake once using the current connection file and prints a sanitized verdict.

Pass `--replace-existing` when the user's request expresses setup/repair/new-token intent or they explicitly approved a replacement. Treat `error_code` plus optional `field` as the complete failure report; never attempt to obtain more detailed file contents.

## Connection Validation

After every successful `all`, `connections`, or `rotate-token` operation, run `scripts/snowflake_setup.py` with `--operation validate --output-dir /work` BEFORE `mcp_assistant_toggle_integration`. It signs in to Snowflake once using the just-written connection file and prints only a sanitized verdict; it never prints the token or any connection-file value.

Validation applies only when this session wrote or rotated the connection file. When no such operation ran — for example `candidate_ready` backed by a `secure_stub` connection — skip validation and enable directly: a stub cannot be validated. If enable returns `saved_secret_unavailable`, that proves the old encrypted value is no longer usable; enter the Secure PAT replacement flow above; collecting a new PAT just to make validation possible is never acceptable. Replace it only when the saved value is explicitly unavailable or the user requested a new token.

- Success (`"validated": true`): proceed to activation.
- `error_code: "auth_rejected"`: report the returned `snowflake_message` to the user verbatim and explain the likely causes in order — the token was mis-pasted, expired, or revoked; or the token's role restriction does not match the `role` in the connection file. Then restart the Secure PAT flow and validate again. If a second freshly minted token is also rejected, stop collecting tokens — the remaining causes are rare org-side issues (for example the Snowflake login name differing from the LDAP short name, or an account policy on the user) that a Snowflake admin should confirm; do not keep asking the user questions or minting tokens.
- `error_code: "legacy_pat_credential"`: the file stores the token under `password` with the PAT authenticator — the shape the connector cannot sign in with. Do not collect a new token and do not rotate: enable the integration — Portico migrates the stored generated file automatically at enable time. If enabling then fails with an auth-shaped error, pivot to the Secure PAT flow.
- `error_code: "network_unreachable"` or `"snowflake_unavailable"`: not a token problem; Snowflake was unreachable or returned a transient service error. Offer to retry validation.
- `error_code: "validation_unexpected_response"`: Snowflake answered with something other than a login verdict. Retry once; if it repeats, proceed to activation and rely on startup monitoring.
- `error_code: "connections_file_stub"`: validation was attempted without a fresh write; follow the skip rule above instead of collecting a new token.
- `missing_required_field` / `invalid_field` / other `connections_file_*` codes: follow the State Decisions routing for an unusable connection file.

## Activation and Failures

Call `mcp_assistant_toggle_integration(server_id="snowflake", enabled=true)` after the required files are ready and — whenever this session wrote or rotated the connection file — Connection Validation succeeded. When `healthy=true` and `readiness_phase="tool_ready"`, activate `server:snowflake` for the chat. Follow returned readiness/action plans without repeatedly toggling. If enabling fails or readiness does not reach tool-ready and the failure looks auth-shaped — or the user already reported a broken token — pivot to the rotate-token Secure PAT flow instead of waiting or re-toggling.

Never call `mcp_assistant_trigger_guided_setup` from this skill. Snowflake file creation and repair are owned by the workspace scripts and secure PAT dialog described above; the generic Configure modal cannot recreate a missing encrypted connection.

For startup failures, fetch up to 200 Snowflake server log lines. Route parser errors to replacement of only `mcp_config.yaml`, authentication errors to the secure PAT flow, non-secret role/warehouse/database/schema errors to corrected metadata, and missing files back through workspace consent and inspection. Do not expose credentials from logs.

Ask before any live Snowflake smoke test, including `SELECT 1`. On success, report that Snowflake is configured and available, and make live testing optional.

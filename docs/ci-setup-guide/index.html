Harbor Registry Setup

04
Create Harbor robot account
Mint a pull/push robot account for the portico Harbor project.

Navigate to harbor.example.invalid → Login via OIDC → select the portico project.

  • Go to Robot Accounts tab
  • Click + New Robot Account
  • Name: portico (the robot$ prefix is added automatically)
  • Grant: Push and Pull permissions for images

The resulting username will look like: robot$portico+portico

! The username contains a $ character. This is critical for the next step -- GitLab variable expansion must be disabled.
# help-harbor Confluence: Harbor Getting Started
05
Configure GitLab CI variables for Harbor
Add HARBOR_USER and HARBOR_TOKEN as protected, masked, raw variables.

Navigate to:

Settings → CI/CD → Variables → Add variable

Add both variables with these exact settings:

VariableProtectedMaskedExpandType
HARBOR_USERYesYesNoVariable
HARBOR_TOKENYesYesNoVariable
! You MUST uncheck "Expand variable reference" for HARBOR_USER. The $ in robot$portico+portico will be interpreted as a variable reference and silently destroyed if expansion is enabled.

These variables are not stored in Vault because the corporate container-images child pipeline template requires inherited GitLab variables (not Vault-injected ones).

Release Broker Setup

06
Protect broker's main branch
Only protected main can access signing credentials.

Navigate to the broker project:

Settings → Repository → Protected branches

Protect main:

  • Allowed to merge: Maintainers
  • Allowed to push and merge: No one
  • No direct pushes permitted
i Because the broker's pipeline always runs on protected main, it has access to Vault secrets and signing credentials. The MR source project never touches these -- only the broker does.
07
Configure reciprocal job-token access
Both projects must allow CI job tokens from each other.

Fine-grained job-token allowlists enable triggering, source cloning, and API access (READ_MERGE_REQUESTS, READ_REPOSITORIES) without long-lived GitLab tokens.

Configure in both projects:

Settings → CI/CD → Token Access

On the source project (portico/portico):

  • Allow CI job tokens from portico/portico-release-broker
  • Grant: READ_MERGE_REQUESTS, READ_REPOSITORIES

On the broker project (portico/portico-release-broker):

  • Allow CI job tokens from portico/portico
  • Grant: Trigger pipelines
i No long-lived GitLab personal or project tokens are needed. The CI job token scoping provides least-privilege access between the two projects.

10
Add daily cleanup scheduled pipeline
Schedule daily pipeline with portico_CLEANUP_ONLY=true for MR release retention.

Navigate to the broker project:

CI/CD → Schedules → New schedule

Set the variable portico_CLEANUP_ONLY=true on the schedule. This causes the pipeline to run only the cleanup job.

Retention rules:

MR StatusRule
Open MRKeep newest release; delete superseded releases after 7 days
Closed / merged MRDelete all releases after 7 days

The cleanup script deletes Cloudsmith packages first, then removes the corresponding Harbor mr-<IID>-<SHA> image tags.

! Without the scheduled cleanup, MR releases will accumulate indefinitely in Cloudsmith and Harbor. Set a reasonable schedule (daily) and verify it runs successfully after setup.
11
Backport trigger to maintained branches
Branches without the mr-release trigger in .gitlab-ci.yml can't use broker releases.

The mr-release job is defined in the repository's .gitlab-ci.yml. Branches that predate this change will not have the trigger job and therefore cannot produce broker-signed MR releases.

Action: Cherry-pick or merge the updated .gitlab-ci.yml into all maintained branches that should support signed MR releases.

i This is only necessary for branches that existed before the broker pipeline was added. New branches created from pre-beta-tmp will automatically include the mr-release trigger.

Apple Code Signing

12
Export Developer ID Application P12
Extract the signing certificate and private key as a base64-encoded .p12 file.

The certificate identity must be exactly:

Developer ID Application: Portico, Inc. (AJDA86F3YP)

Export from macOS Keychain Access:

  • Open Keychain Access → search for "Developer ID Application"
  • Expand the certificate to show the private key
  • Select both the certificate AND private key
  • File → Export Items → save as .p12 with a strong password
  • Base64-encode: base64 -i cert.p12 > cert.p12.b64

Or use an existing Vault path -- the Rookery team stores this certificate in the community namespace at:

# Rookery's existing location (community namespace, for reference) P12 cert: secret-units/gitlab-ci/secrets/codesign-p12 Password: secret-units/gitlab-ci/secrets/codesign-p12-password

Copy the P12 and password into our own namespace at gitlab-ci/release-secrets (Step 03).

i This certificate expires February 1, 2027. The CI scripts include a preflight warning 60 days before expiry and will fail within 14 days of expiration.

16
Obtain Cloudsmith entitlement token
The read/download token embedded in the app for first-launch update discovery.

The entitlement token is the read-only download credential. It's embedded in the signed app bundle and managed-runtime bootstrap resource so first-launch update/repair can authenticate with Cloudsmith.

The token can be sourced from:

  • The release environment variable CLOUDSMITH_ENTITLEMENT_TOKEN
  • The source cloudsmith.env file
  • The release operator's macOS Keychain (service: portico, account: CLOUDSMITH_ENTITLEMENT_TOKEN)

Store both CLOUDSMITH_API_KEY and CLOUDSMITH_ENTITLEMENT_TOKEN in Vault at the release secret path (Step 03).

Validate & Pilot

17
Pilot: MR broker release
Verify signed per-MR release via the broker pipeline.

Open an MR targeting pre-beta-tmp. The MR pipeline runs: metadata, test, mr-release (trigger). The broker pipeline then runs validation, staging, signing, and publishing. Every MR commit gets a fully signed, notarized release.

Each MR gets channel mr-<IID>, package portico_mr-<IID>, image tag mr-<IID>-<SHA>.

Verify each stage:

StageExpected Result
metadataEmits release.env with channel=mr-<IID>
testAll tests pass
mr-releaseTriggers broker, mirrors result back
Broker validateMR is open, same-project, SHA matches
Broker stageUnsigned app bundles built, no credentials
Broker packageSigned, notarized, stapled
Broker publishUploaded to portico_mr-<IID>

Checklist:

  • App signed with Developer ID Application: Portico, Inc. (AJDA86F3YP)
  • No secrets visible in MR pipeline logs (secrets only in broker)
  • Fork MR is blocked (only metadata + test run)
  • Client configured on mr-<IID> channel discovers the update
18
Pilot: Cleanup verification
Verify daily cleanup removes expired MR releases.

After the scheduled cleanup pipeline runs (daily with portico_CLEANUP_ONLY=true), verify the retention rules are applied:

  • Superseded MR releases older than 7 days are purged from Cloudsmith
  • Closed/merged MR releases older than 7 days are purged from Cloudsmith
  • Corresponding Harbor mr-<IID>-<SHA> image tags are removed
  • The newest release for each open MR is preserved
i Trigger the cleanup manually the first time to verify it works: run a pipeline on the broker's main with the variable portico_CLEANUP_ONLY=true.
19
Pilot: Protected merge and beta promotion
Merge to pre-beta-tmp and verify the full signed release pipeline, then promote to beta.

Merge the MR into pre-beta-tmp. This triggers the complete protected push release chain:

metadata → test → host-binaries → runtime-images (x7) → verify → signed-package → publish-cloudsmith → promote-latest

Verify each stage:

  • All 7 runtime images pushed to Harbor with full-SHA tag
  • Attestation JSON validates 7 images x 2 platforms
  • Apps signed with Developer ID Application: Portico, Inc. (AJDA86F3YP)
  • Both .app bundles pass codesign --verify --deep --strict
  • Both .app bundles pass spctl --assess (Gatekeeper)
  • Notarization tickets stapled via xcrun stapler validate
  • Release ZIP uploaded to Cloudsmith portico_dev
  • All 7 Harbor images promoted to latest tag

Beta promotion: Merge pre-beta-tmp into beta. Verify channel is beta, package is portico_beta, both architectures present, and end-to-end update discovery works.

Idempotence and serialization: Retry publish-cloudsmith to verify --republish idempotence. Push two rapid commits to verify assert-release-branch-tip.sh staleness protection. Confirm resource_group serialization prevents concurrent releases.

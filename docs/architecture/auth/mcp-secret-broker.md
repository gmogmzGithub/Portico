# MCP Secret Broker Architecture

The MCP secret broker is the host-mediated secret delivery path introduced by `69c5278a`. It replaces broad Docker mounts and durable container-side OAuth token files with scoped, request-time vending through the Host MCP Bridge.

## Purpose

Before the broker, MCP runtimes could receive mounted OAuth token/client files or host runtime-secret files. That made container compromise or misconfiguration more expensive: a runtime could potentially inspect durable material wider than the single server it owned.

The broker changes the contract:

- Durable OAuth records live in Electron `safeStorage` under app `userData`.
- Containers receive only runtime material they are scoped to use.
- OAuth runtimes receive access-token material, not the durable host record.
- Static sensitive env/runtime-file values are materialized into the owning container on demand.
- Missing records fail closed and surface OAuth/setup-required state.

## Actors

| Actor | Runs where | Responsibility |
|---|---|---|
| MCP runtime container | Docker | Starts `mcp-orc`/MCP server and requests scoped runtime material |
| Host MCP Bridge | Host loopback, usually port `8891` | Authenticates scoped container token and proxies broker request |
| Electron API | Host loopback, usually port `9876` | Owns durable secret stores and validates internal broker auth |
| Electron safeStorage / Keychain | Host OS | Durable encrypted OAuth records and runtime-secret backing stores |

## Endpoint Topology

```text
Container
  POST http://host.docker.internal:8891/secrets/oauth/access-token
  POST http://host.docker.internal:8891/secrets/static-secret
      Authorization: Bearer <scoped bridge token>
        │
        ▼
Host MCP Bridge
  validates bearer token and exact scope
        │
        ▼
Electron API
  POST http://127.0.0.1:9876/api/mcp/oauth/record
  POST http://127.0.0.1:9876/api/mcp/oauth/record/update
  POST http://127.0.0.1:9876/api/mcp/static-secret
      Authorization: Bearer <internal broker token>
```

The Electron-facing internal broker token is `HOST_MCP_BRIDGE_ELECTRON_BROKER_TOKEN`. It is generated by Electron for the app process/bridge relationship and checked with timing-safe comparison.

## Scopes

Scoped bridge tokens use simple exact-match strings:

| Scope | Meaning |
|---|---|
| `oauth:access-token:<server_id>` | May request OAuth access-token material for exactly one server |
| `static-secret:<server_id>:<secret_name>` | May request exactly one static secret for exactly one server |

The bridge validates `server_id` and `secret_name` path-safely before checking scope. A Slack runtime token cannot ask for Glean's OAuth record, and a runtime-file token cannot ask for a different secret name.

## OAuth Happy Path

```text
1. Compose generation detects an OAuth-enabled server.
2. Electron creates a scoped bridge token for oauth:access-token:<server_id>.
3. The generated service receives:
   - portico_OAUTH_ACCESS_TOKEN_BROKER_URL
   - portico_OAUTH_ACCESS_TOKEN_SERVER_ID
   - portico_OAUTH_ACCESS_TOKEN_BROKER_TOKEN
4. mcp-orc detects broker env and asks the broker for an access token.
5. Host MCP Bridge validates the bearer token and scope.
6. Electron loads the safeStorage OAuth record.
7. Rust bridge refreshes if needed and writes updates back through Electron.
8. Container seeds runtime OAuth state and starts the MCP server.
```

In broker mode, container-side OAuth storage is runtime-only. The host safeStorage record remains the durable source of truth.

## Legacy Migration Path

When Electron receives an OAuth broker request, it first attempts to migrate legacy OAuth records if needed:

1. Look for legacy records under `mcpo-oauth-tokens` and `mcpo-core-oauth-tokens`.
2. Use the Rust `export-legacy-oauth-record` command to normalize old token/client files.
3. Persist the normalized record into Electron safeStorage.
4. Verify the safeStorage round trip.
5. Remove legacy files and record migration status.

If migration is impossible or secure storage is unavailable, the broker returns an auth-required/fail-closed response rather than falling back to plaintext durable storage.

## Empty safeStorage / First-Time OAuth

When no safeStorage record and no migratable legacy record exist, the broker returns `428` with `auth_required: true` and reason `secure_record_missing`.

This is the critical edge case for broker correctness: a setup-only single-server container that is launched with access-token broker env but no durable record exists can never produce the first authorization URL — broker-mode startup bails with `auth_required` *before* generating a container-local URL, so the wizard waits forever (observed historically as a `connection refused`/`authorization required` loop with no path forward but manual retry).

### Bootstrap Mode (implemented)

The interactive wizard/single-server stack therefore runs in a dedicated **bootstrap mode** that omits access-token broker env so the container can perform the full first-time handshake itself, then exports the captured record back to Electron `safeStorage`:

```text
User starts OAuth setup
  └─ Electron mints a one-time export bearer (crypto.randomBytes) and launches the
     single-server stack via start-single-mcp-server.sh --oauth-bootstrap
       └─ Bootstrap mode OMITS the access-token broker trio and instead injects
          portico_OAUTH_BOOTSTRAP_EXPORT_TOKEN
            └─ Rust OAuth runtime builds a container-local authorization URL
                 └─ Browser callback returns to the same single-server runtime,
                    which exchanges the code and captures token + client info
                      └─ On completion Electron calls
                         POST /oauth/bootstrap-record/{server_name} (bearer-guarded)
                           └─ Electron persists the record into safeStorage
                              (persistOAuthRecord); main/runtime containers then use
                              normal broker vending/refresh
```

Key properties:

- **Bootstrap vs. broker is selected per launch.** `start-single-mcp-server.sh --oauth-bootstrap` omits `portico_OAUTH_ACCESS_TOKEN_BROKER_URL/_SERVER_ID/_BROKER_TOKEN` and requires `portico_OAUTH_BOOTSTRAP_EXPORT_TOKEN`; the default (non-bootstrap) path keeps the broker trio. The main/runtime stack is unchanged and always broker-mode.
- **The export endpoint only exists during bootstrap.** `POST /oauth/bootstrap-record/{server_name}` returns `404` unless `portico_OAUTH_BOOTSTRAP_EXPORT_TOKEN` is set, is guarded by that one-time bearer (constant-time compare), responds `Cache-Control: no-store`, and normalizes the token to carry an absolute `expires_at`. The raw token never leaves the Electron main process.
- **Import is fail-closed.** Electron only reports OAuth success after the record is persisted to safeStorage; if export/import fails, the flow reports failure rather than losing the credential. The one-time bearer is dropped immediately after a successful import.
- **Static-secret broker behavior is unchanged in bootstrap mode** — only the OAuth *access-token* broker trio is omitted.

Do not treat `auth_required` from the broker as a usable token state. It means durable host authorization is missing or unusable; the resolution is the bootstrap flow above (or repairing migration), never falling back to plaintext.

## Refresh Path

When a runtime receives an unauthorized response or needs forced refresh:

1. The runtime calls `/secrets/oauth/access-token` with `force_refresh: true`.
2. The bridge fetches the full safeStorage record from Electron.
3. Rust OAuth code refreshes using server metadata/client info.
4. The bridge posts the updated token/client info to Electron `/api/mcp/oauth/record/update`.
5. The refreshed access token is returned to the runtime.

This keeps refresh-token persistence host-side while still letting existing MCP server code receive an access token in the shape it expects.

## Static Secret Materialization

For sensitive `required_env_vars` and `runtime_files`, compose generation emits:

- `portico_STATIC_SECRET_BROKER_URL`
- `portico_STATIC_SECRET_TARGETS`
- one `portico_STATIC_SECRET_TOKEN_*` variable per target

`portico_STATIC_SECRET_TARGETS` is a semicolon-separated manifest. Each entry is:

```text
<server_id>|<secret_name>|<write_path>|<token_env>|<optional_link_path>
```

At container startup, `start-mcpo.sh` reads the manifest, sends one broker request per entry, verifies the returned identity, base64-decodes the payload, and writes the target file with private permissions. Optional link paths let file-shaped secrets appear at the MCP server's expected container path while the broker materializes them inside an internal tmpfs directory.

## Environment Contract

| Variable | Consumer | Purpose |
|---|---|---|
| `portico_OAUTH_ACCESS_TOKEN_BROKER_URL` | OAuth runtime container | Host bridge URL for access-token vending |
| `portico_OAUTH_ACCESS_TOKEN_SERVER_ID` | OAuth runtime container | Canonical server ID to request |
| `portico_OAUTH_ACCESS_TOKEN_BROKER_TOKEN` | OAuth runtime container | Scoped bearer token for that server |
| `portico_OAUTH_BOOTSTRAP_EXPORT_TOKEN` | Single-server bootstrap container | One-time bearer guarding `POST /oauth/bootstrap-record/{server_name}`; present only in `--oauth-bootstrap` (first-time) launches, omitted in broker mode |
| `portico_STATIC_SECRET_BROKER_URL` | MCP container entrypoint | Host bridge URL for static-secret vending |
| `portico_STATIC_SECRET_TARGETS` | MCP container entrypoint | Static-secret materialization manifest |
| `portico_STATIC_SECRET_TOKEN_*` | MCP container entrypoint | Scoped bearer token for one static secret |
| `portico_STATIC_SECRET_AVAILABLE_<SERVER>_<SECRET>` | MCP configuration generator | Presence signal set to `1` only after startup verifies the sensitive runtime file exists in Keychain |
| `HOST_MCP_BRIDGE_ELECTRON_OAUTH_BROKER_URL` | Host MCP Bridge | Electron URL for durable OAuth record loading |
| `HOST_MCP_BRIDGE_ELECTRON_OAUTH_UPDATE_URL` | Host MCP Bridge | Electron URL for durable OAuth record updates |
| `HOST_MCP_BRIDGE_ELECTRON_OAUTH_INVALIDATE_URL` | Host MCP Bridge | Electron URL for terminal OAuth record invalidation and reauthorization tombstones |
| `HOST_MCP_BRIDGE_ELECTRON_STATIC_SECRET_BROKER_URL` | Host MCP Bridge | Electron URL for static-secret resolution |
| `HOST_MCP_BRIDGE_ELECTRON_BROKER_TOKEN` | Host MCP Bridge and Electron | Internal bearer token between bridge and Electron |

## Failure Modes

| Symptom | Meaning | Expected behavior |
|---|---|---|
| Broker returns `401` | Missing or invalid bridge/Electron bearer token | Fail closed; regenerate scoped token or restart bridge |
| Broker returns `403` | Token is valid but lacks exact scope | Fail closed; investigate token registry/generation |
| Broker returns `428 auth_required` | Durable OAuth record is missing/unusable | Launch OAuth setup or repair migration |
| Broker returns `503` | Electron broker or secure storage unavailable | Fail closed; do not fall back to plaintext |
| Static-secret materialization fails | Secret missing, scope mismatch, invalid payload, or broker down | Container startup should fail loudly |

# Security Hardening Overview

**Audience:** engineers and security reviewers.

This document captures the current state of security hardening in
Portico. It spans the **Electron Shell**, **IPC/Communication**,
**Docker Orchestration**, **MCP Orchestration**, **LLM Routing**, **Chat
UI**, **State & Persistence**, **Health Check & Configuration**, and
**Update & Distribution** layers. The threat-model identifiers (`N-…`,
`V-…`) below cross-reference the internal PORTICO threat-model report.

For the per-action tool-confirmation gate model, see
[`tool-confirmation.md`](tool-confirmation.md). For the forward-looking
Vault plan that supersedes parts of the current secret bootstrap, see
[`vault-prerequisites.md`](vault-prerequisites.md).

## 1) Before vs after

| Area | Before | After | Layer(s) |
|---|---|---|---|
| Runtime secret policy | Secret handling depended on caller/path | Centralized runtime secret registry with explicit key scope + write policy | State & Persistence, Electron Shell |
| Runtime secret writes | Runtime writes could drift by feature path | Writes restricted to explicit runtime-allowed keys | IPC/Communication, State & Persistence |
| Secure local storage | Mixed plaintext and ad hoc persistence | Keychain-first flow on macOS with keychain-only mode; post-Keychain auto-scrub on packaged macOS (`buildRuntimeSecretEnv` → `stripEnvKeysFromPaths`) removes the canonical runtime keys from all managed-root/resources-path plaintext sources (`runtime-secrets.env`, the upstream `PORTICO_LLM_API_KEY` file, and `cloudsmith.env`'s `CLOUDSMITH_ENTITLEMENT_TOKEN`) and from the project-root `.env` after successful Keychain persistence | Electron Shell, State & Persistence |
| Plaintext strip scope | Strip lists only covered canonical key names | Expanded to runtime aliases (`INTERNAL_OPENAI_API_KEY`, `BIFROST_BRIDGE_LOCAL_API_KEY`, `OPENAI_API_KEY`) and every active `_FILE` variant so guided setup, runtime bootstrap, and the compose cleaner agree. The repository `.env` `CLOUDSMITH_API_KEY` is protected release-operator input and is excluded from generic stripping; only managed `cloudsmith.env` copies use the verified Keychain-persistence scrub lifecycle. | State & Persistence, Docker Orchestration, Chat UI |
| Plaintext candidate read paths | Runtime and Cloudsmith secrets could be hydrated from project-root `runtime-secrets.env` / `cloudsmith.env` | Secret resolvers (Node + shell) restricted to managed-root, resources-path, and explicit overrides; project root plaintext twins are ignored | Electron Shell, State & Persistence |
| Cloudsmith token separation | Read and upload semantics were mixed at runtime | Packaged update discovery uses `CLOUDSMITH_API_KEY`, matching the working `beta-latest` contract, while raw payload downloads use `CLOUDSMITH_ENTITLEMENT_TOKEN`; runtime child environments and orchestrated containers still exclude the API key | Update & Distribution, Electron Shell |
| Container secret ingress | Raw `PORTICO_LLM_API_KEY` / `BIFROST_BRIDGE_LOCAL_API_KEY` were passed into Bifrost through the container environment | Bifrost and both mcpo services consume secrets exclusively through Docker Compose `secrets:` (read-only tmpfs at `/run/secrets/*`). Host source files live under a user-scoped cache dir (`$HOME/Library/Caches/portico/runtime-secrets` on darwin, `$XDG_STATE_HOME/portico/runtime-secrets` on linux; overridable via `PORTICO_RUNTIME_SECRET_CACHE_DIR`) with `0700` directory and `0600` file permissions, re-materialized by `prepare_optional_file_secret_ingress` on every start and reclaimed by `cleanup_runtime_secret_tmpdir` from the explicit `stop`/`down` path. The dir outlives the orchestration script invocation because `docker compose up -d` detaches and containers bind-mount the files for the stack's lifetime. Compose declarations fall back to `/dev/null` so read-only compose operations (`config`, `build`, `down`, `pull`, `logs`) work without the ingress helper; real `up`/`start` paths go through `src/scripts/docker-compose.sh` and override each `_FILE` with the cache-dir path. A stray `docker compose up` without that ingress mounts an empty `/dev/null` and Bifrost/mcpo refuse to start (fail-loud at the application layer) | Docker Orchestration, MCP Orchestration |
| OAuth durable-token isolation | OAuth token/client files could be mounted into MCP runtimes | Durable OAuth records live in Electron safeStorage. Containers receive only scoped broker-vended runtime material, legacy `.mcpo` / `mcpo-oauth-tokens` mounts are retired, and OAuth records are keyed by canonical `server_id` so single-server and full-stack promotion share consent state. Architecture: [`../architecture/auth/mcp-secret-broker.md`](../architecture/auth/mcp-secret-broker.md). | MCP Orchestration, State & Persistence |
| MCP required-env secret isolation | Per-server API/bearer tokens marked in YAML could still ride through project `.env` into every container | `required_env_vars[].sensitive: true` is now the canonical signal. Electron, shell startup helpers, Rust/shell generators, guided setup/finalize/reconfigure, and the single-server wizard derive the secure path from that metadata: Keychain account `<ENV_VAR>`, Docker secret `<lowercase_sanitized_env_var>`, container env `<ENV_VAR>_FILE=/run/secrets/<secret>`, and raw value materialized only at the MCP child-process boundary. Sensitive keys and `_FILE` variants are stripped from `.env`, `.env.runtime`, managed runtime mirrors, and generated env content; conflicting sensitivity declarations fail generation. | MCP Orchestration, Docker Orchestration, State & Persistence |
| MCP sensitive runtime-file isolation | Complex MCPs could require config files that contain bearer material, and `runtime_files` mounted those files directly from the user's home directory | `runtime_files[].sensitive: true` is now the canonical signal for file-shaped MCP secrets. The source file is treated as a user-owned provisioning input: it is imported into Keychain under `MCP_RUNTIME_FILE::<server_id>::<target_hash>` and mounted into the owning MCP runtime through Docker Compose `secrets:` at the exact configured container target — the source file itself is never overwritten (PORTICO-374; a shared well-known path like `~/.snowflake/connections.toml` is also read by external tools). An in-memory content-hash gate limits Keychain writes to one per app launch per file; editing the source file rotates the credential on the next resolve. Legacy stubs written by earlier builds are restored from Keychain once per session when the file is exactly the stub. Non-sensitive runtime files continue to use read-only bind mounts. Snowflake marks `~/.snowflake/connections.toml` sensitive so its PAT-bearing TOML file is never bind-mounted directly from the user's home directory, while the shared file stays intact for Cortex Code, Streamlit, and the Snowflake CLI. | MCP Orchestration, Docker Orchestration, State & Persistence |
| Project `.env` container delivery | Base Compose, generated MCP Compose, Open WebUI, Bifrost bridge, and health-check could receive project `.env` directly or through `env_file` | No service consumes `env_file: .env`, and health-check no longer bind-mounts `.env` as `/app/user.env`. Non-secret config is explicit environment, sensitive config is Docker-secret file ingress, and Rust health-check reads generated configured-status metadata that records only configured/missing state and names, never values. | Docker Orchestration, Health Check & Configuration |
| Host-mode MCP isolation | Host-mode servers inherited the user's full login-session filesystem and Keychain reachability | Host MCP startup now writes private SRT settings and wraps `mcp-orc` under `@anthropic-ai/sandbox-runtime`, with an outer macOS Seatbelt profile denying project secret files, runtime secret cache files, `~/.ssh`, Keychains, `/usr/bin/security`, and securityd/SecurityServer mach lookups. Host server YAML `allowed_domains` controls network allowlisting; Chrome DevTools defaults to loopback-only. No unsandboxed fallback is allowed once host MCP sandbox prep fails. | MCP Orchestration, Electron Shell |
| Local gateway auth | Local bearer path had mismatch/coverage issues | Protected-route bearer auth tightened, route exceptions explicit | LLM Routing, IPC/Communication |
| UI model discovery auth | UI could call gateway with wrong token contract | UI-to-gateway bearer wiring aligned to local gateway contract | Chat UI, LLM Routing |
| Connectivity diagnostics | Reachability checks could fail on non-200 but reachable responses | HTTP-status-aware reachability for Cloudsmith probe | Health Check & Configuration |
| FTS regex search safety | Regex mode had ReDoS/fallback wildcard risk | Added safer regex handling and dedicated security tests | State & Persistence, Chat UI |
| Guided setup secret leakage risk | Runtime-only keys could leak into generated env output | Guided setup consistently strips runtime-only secret keys including alias and `_FILE` variants | Chat UI, State & Persistence |
| Probe command construction | Shell command strings assembled with interpolated values | Argument-based process invocation in probe path | IPC/Communication, Electron Shell |
| Installer secret bootstrap | Installer could finish without stable secure secret bootstrap | Installer now provisions runtime-required secrets into secure storage | Update & Distribution, Electron Shell |
| Regression coverage | No automated coverage for strip/scrub/compose-secret paths | Added Node unit tests (`runtime-secrets-hardening.unit.test.js`) and a shell regression (`tests/test_docker_compose_runtime_secrets.sh`) wired into the smoke gate | State & Persistence, Docker Orchestration |
| Refactor quality | Secret persistence paths had duplicated branch logic | Consolidated keychain-account mapping and branch simplification | State & Persistence |
| MCP write/action authorization | Destructive MCP tools (Slack post-message, Gmail send, Drive / Docs / Sheets / Slides mutations, GitLab / Jira / Confluence writes, n8n workflow runs, data-platform query execution, etc.) could be invoked by the LLM without an explicit per-action user confirmation; a stale "yes" from earlier in the chat or a model that decided to act unprompted could trigger external side effects | Per-action runtime confirmation gate (`src/patches/backend/open_webui/utils/tool_confirmation_gate.py`) classifies every tool call against [`mcp-policy/destructive-tools.json`](../../mcp-policy/destructive-tools.json), blocks destructive calls until the user explicitly confirms THIS exact tool + args via the new `<ToolConfirmationChip>` rendered in the chat input frame (Yes / No / reply-with-changes), binds approval to a per-call hash so any argument or tool-name drift fails closed, drops pending after every user turn so consent never leaks across turns, and pairs with a `## Tool Action Policy` block injected into the system prompt and a hardened Slack skill prompt that teach the model to surface the action in plain text before calling. Audit events `proposed` / `approved` / `cancelled` / `modified` / `expired` / `hash_mismatch` / `gate_bypass_attempted` / `dispatched_*` cover the full lifecycle. Threat model: N-012. Test plan: L-18..L-23, G-30..G-32 | MCP Orchestration, Chat UI, IPC/Communication |

| `N-012` | MCP write/action tools could fire on the user's behalf without a fresh, action-specific confirmation. The risk surfaced once Slack OAuth landed with `SLACK_MCP_ADD_MESSAGE_TOOL=true` and the `chat:write` / `im:write` / `mpim:write` scopes — exposing destructive Slack tools with no runtime gate between the assistant and the dispatcher meant a stale "yes" earlier in a chat (or a model that decided to proactively act before being asked) could send a Slack DM, an email, a calendar invite, etc. without explicit per-action consent. Affects every destructive MCP tool catalogued in [`tool-confirmation.md`](tool-confirmation.md), including Slack, Gmail, Drive / Docs / Sheets / Slides, GitLab, Jira / Confluence, n8n, the data platform, and the notifications MCP | **Resolved** | Two layers, designed to be useful even if either one regresses independently:<br>**Hard layer (runtime gate).** `src/patches/backend/open_webui/utils/tool_confirmation_gate.py` defines a `Gate` that classifies every tool call against [`mcp-policy/destructive-tools.json`](../../mcp-policy/destructive-tools.json). Read-only tools dispatch immediately; destructive tools are blocked on first call — a stable per-call hash bound to `(tool_name, canonicalized_args)` is registered as a *pending* action and a `chat:tool_confirmation` event is emitted to the renderer. The user's next message goes through `Gate.resolve_user_reply`, which is intentionally strict: a strict-affirmative match (`yes`, `y`, `do it`, `send it`, `go ahead`, `ok`, `confirm`, `approve`) authorizes ONLY when exactly one chip is pending; an affirmative with multiple pending chips drops everything as ambiguous (this is the exact failure mode the original incident exercised). A strict-negative cancels. Anything else is treated as `modify`: pending entries drop and the text is forwarded to the model as a normal turn. Approval marks the matching hash as approved-for-one-dispatch — the model can then re-emit the call without the model itself knowing about the token; the gate consumes the matching hash on dispatch and `consume_assistant_turn` drops any unused approval at end of assistant turn so consent never leaks across turns. Argument or tool-name drift between approval and dispatch fails closed as `hash_mismatch`. Forged or replayed tokens fail closed as `gate_bypass_attempted`. The gate is wired into `process_chat_payload` (resolves the user reply, injects the policy block, clears stale pending) and into `chat_completion_tools_handler::tool_call_handler` (intercepts the dispatch elif chain so MCP, OpenAPI/external, direct, and local-Python tool paths all funnel through `_apply_tool_confirmation_gate`). Audit events `proposed`, `approved`, `cancelled`, `modified`, `expired`, `hash_mismatch`, `gate_bypass_attempted`, `dispatched_safe`, `dispatched_after_approval` are emitted via the `audit_log_fn` callback (default: structured stdlib log). UI surfaces a `<ToolConfirmationChip>` in [`src/patches/frontend/src/lib/components/chat/MessageInput/ToolConfirmationChip.svelte`](../../src/patches/frontend/src/lib/components/chat/MessageInput/ToolConfirmationChip.svelte) — rendered above the chat composer alongside the Pending Steer chip — with Yes / No / "reply with changes" actions; Yes/No buttons funnel through `window.postMessage({type: 'input:prompt:submit', ...})` — the same input pipeline a hand-typed reply uses — so the chip has no privileged side channel and the gate's natural-language resolver remains the single source of truth. State is owned by [`src/patches/frontend/src/lib/components/chat/Chat.svelte`](../../src/patches/frontend/src/lib/components/chat/Chat.svelte) (chat-scoped `pendingToolConfirmations` list, dropped on user submit, chat switch, and rejection) so consent never leaks across turns or chats at the renderer layer either.<br>**Soft layer (prompt policy).** `tool_confirmation_gate.inject_tool_action_policy` prepends a `## Tool Action Policy (mandatory)` block to the system prompt on every chat turn, teaching the model to surface the action in plain text and ask a direct yes/no question before calling. [`skills/slack/SKILL.md`](../../skills/slack/SKILL.md) was hardened for the same contract on `slack_conversations_add_message`. The policy alone is not the defense — the runtime gate is — but it makes the "right" path (model proposes -> user approves -> gate dispatches) the default the model picks even before the gate ever has to fire.<br>Test surface: 37 unit tests in [`tests/test_tool_confirmation_gate.py`](../../tests/test_tool_confirmation_gate.py) cover registry classification, hashing, summary rendering, gate evaluate/resolve, single-use semantics, per-chat isolation, audit logging, and policy injection. 8 end-to-end scenarios in [`tests/test_tool_confirmation_gate_end_to_end.py`](../../tests/test_tool_confirmation_gate_end_to_end.py) drive a fake destructive dispatcher and assert no dispatch happens without a fresh confirmation — including the exact "planning yes far from the propose" pattern of the original incident. Renderer smoke tests in [`tests/test_tool_confirmation_chip.node.test.js`](../../tests/test_tool_confirmation_chip.node.test.js) lock down the Yes/No/reply contract, keyboard activation, fail-closed state transitions, concurrent-chips behaviour, and the anchoring invariant that the chip is rendered from `MessageInput.svelte` and never inline inside a message bubble. Manual + automated test plan scenarios at [`testing/plan/security/tool-confirmation-gate.md`](../testing/plan/security/tool-confirmation-gate.md) (L-18..L-23) and [`testing/plan/mcp/tool-confirmation.md`](../testing/plan/mcp/tool-confirmation.md) (G-30..G-32) | Track upstream MCP server additions: every new MCP that lands under `mcp-configs/` must add (or be confirmed read-only against) the catalogue in [`tool-confirmation.md`](tool-confirmation.md) and the rules in [`mcp-policy/destructive-tools.json`](../../mcp-policy/destructive-tools.json) (G-32 in the test plan covers this gate). Wire the gate's audit callback into the chat audit pipeline so `proposed` / `approved` / `cancelled` / `modified` / `gate_bypass_attempted` events are persisted alongside chat history and surfaced to security on demand. Pursue an in-chip edit affordance (currently free-text edits go through the chat composer) once UX validates demand. ## 3) Final Key/Token Usage Table

Runtime key delivery now separates the *host* resolution path (Keychain-first on packaged macOS, with a controlled set of plaintext fallbacks) from the *container* delivery path (Docker Compose `secrets:` mounting each value as a read-only tmpfs file at `/run/secrets/<name>`). The orchestration script (`src/scripts/docker-compose.sh`) materializes the host-side source files under a user-scoped cache directory (`0700`/`0600` permissions; see `_default_runtime_secret_cache_dir` for the per-OS paths) and reclaims the directory via `cleanup_runtime_secret_tmpdir` on the explicit `stop`/`down` path. The cache dir deliberately outlives any single `docker-compose.sh` invocation because `docker compose up -d` detaches and the containers' bind-mount sources must remain on the host for the stack's lifetime.

| Key / token | Primary use | Install-time handling | Runtime source order (host) | Container delivery | At-rest state | Runtime exposure |
|---|---|---|---|---|---|---|
| `PORTICO_LLM_API_KEY` | Upstream LLM provider credential | Provisioned into secure storage | env -> Keychain -> controlled fallback (installer/managed-root/resources only) | Docker secret `/run/secrets/portico_llm_api_key`, read by Bifrost via `PORTICO_LLM_API_KEY_FILE` | Keychain-preferred; managed-root plaintext only when Keychain disabled, auto-scrubbed on packaged macOS after Keychain persistence succeeds | Plaintext in process memory when used |
| `LOCAL_STACK_API_KEY` | Local internal auth root key | Generated/provisioned per install | env aliases -> Keychain -> managed-root fallback -> generated | Not delivered to containers directly; fans out into `INTERNAL_OPENAI_API_KEY`, `BIFROST_BRIDGE_LOCAL_API_KEY`, `OPENAI_API_KEY` on the host | Keychain-preferred | Plaintext in runtime memory/env where consumed |
| `OPENAI_API_KEY` | Runtime alias for local internal key paths; consumed by OWUI and health-check containers that do not yet support `_FILE` ingress | Derived from runtime secret env build | Fan-out from `LOCAL_STACK_API_KEY` | Passed as env var to OWUI / health-check only; no longer used as the mcpo OAuth encryption key | Alias (not a separate secure source) | Plaintext alias at runtime |
| `INTERNAL_OPENAI_API_KEY` | Internal alias for local internal key | Derived | Fan-out from `LOCAL_STACK_API_KEY` | Env alias on the host only | Alias | Plaintext alias at runtime |
| `BIFROST_BRIDGE_LOCAL_API_KEY` | Internal alias for local internal key (legacy Bifrost bridge path) | Derived | Fan-out from `LOCAL_STACK_API_KEY` | Env alias on the host only | Alias | Plaintext alias at runtime |
| `BIFROST_BRIDGE_LOCAL_API_KEY` | Local bearer auth for gateway protected routes | Provisioned/generated and persisted | env -> Keychain -> managed-root fallback -> generated | Docker secret `/run/secrets/bifrost_bridge_local_api_key`, read by Bifrost via `BIFROST_BRIDGE_LOCAL_API_KEY_FILE`; OWUI continues to receive it as `OPENAI_API_KEY` env var (no native `_FILE` ingress upstream) | Keychain-preferred | Plaintext in memory/env for auth checks |
| `CLOUDSMITH_ENTITLEMENT_TOKEN` | Read-only Cloudsmith runtime/install/update access | Provisioned into secure storage | env -> Keychain -> managed-root/resources `cloudsmith.env` | Not delivered into orchestrated containers | Keychain-preferred | Plaintext in memory/env only while used |
| `CLOUDSMITH_API_KEY` | Cloudsmith package discovery plus release upload key | Provisioned at release time | Embedded in the signed app `cloudsmith.env` for Electron updater discovery | Never delivered to orchestrated containers or runtime child processes | Packaged resource plus release environment | Readable from the packaged app by accepted compatibility contract |
| Slack PKCE public client ID | Slack app OAuth public client identifier | Inline public value in `mcp-configs/slack/slack.fragment`: `2317524819.11152506261415`. There is no Slack OAuth client secret in the app. | Static config only. Legacy `SLACK_OAUTH_CLIENT_ID` / `SLACK_OAUTH_CLIENT_SECRET` env keys are ignored and scrubbed, not used as sources. | No Docker secret, no `_FILE` env var, and no container secret mount. Rust OAuth sends `client_id` plus PKCE fields and never sends `client_secret`. | Public identifier only; no secret at rest. Legacy token/client artifacts are cleared once so users reconnect through PKCE. | Public `client_id` in OAuth URLs and token/refresh requests |
| MCP `required_env_vars[].sensitive: true` values (today: `GITLAB_PERSONAL_ACCESS_TOKEN`, `SOURCEGRAPH_TOKEN`) | Per-server MCP API/bearer tokens | Guided setup, finalize, reconfigure, launch migration, and shell startup discover them dynamically from YAML; no hardcoded per-server registry is required | env (only as migration ingress) -> Keychain account `<ENV_VAR>` -> no plaintext fallback. Plaintext `.env` / `.env.runtime` / managed mirrors are stripped after successful persistence; failures abort rather than falling back | Docker secret `/run/secrets/<lowercase_sanitized_env_var>` mounted only into the owning MCP runtime or combined group; container env exposes only `<ENV_VAR>_FILE`; raw value is read and injected only into that server's spawned MCP child process, including nested `docker run -e KEY` commands | macOS Keychain persistent store; 0600 session file in runtime-secrets cache while stack is running | Plaintext only in the owning MCP child process memory/environment |
| MCP `runtime_files[].sensitive: true` files (today: Snowflake `connections.toml`) | File-shaped MCP credentials that must appear at exact container paths | MCP YAML marks the file sensitive; source is consumed as the provisioning/import path and left in place on disk (content-hash gate re-imports only when the file changes; editing the file rotates the credential) | source file -> Keychain account `MCP_RUNTIME_FILE::<server_id>::<target_hash>` as base64 -> user-scoped runtime-secret cache | Docker secret mounted at the configured target, e.g. `/root/.snowflake/connections.toml`; no direct bind mount from `~/.snowflake/connections.toml` | Keychain-preferred; 0600 session file in runtime-secrets cache while stack is running; the user-owned source file remains at its path (plaintext at rest is accepted for this shared config — container delivery never bind-mounts it); legacy stubs from earlier builds are restored from Keychain once per session | Plaintext only inside the owning MCP runtime container at the target path |

The internal `_FILE` paths (`PORTICO_LLM_API_KEY_FILE`, `BIFROST_BRIDGE_LOCAL_API_KEY_FILE`, plus dynamically discovered MCP sensitive-env `_FILE` keys) are implementation details of the ingress helper; they point at user-owned `0600` files inside the cache directory described above. They are listed in `RUNTIME_SECRET_ENV_FILE_KEYS` / `RUNTIME_SECRET_STRIP_KEYS` or discovered from `required_env_vars[].sensitive: true` so guided setup, runtime bootstrap, and the compose cleaner all refuse to persist them into project-level `.env` files. Legacy Slack OAuth client `_FILE` keys remain scrubbed but are no longer generated.

## 4) No-regression assessment for N-012 (tool-confirmation gate)

The N-012 fix introduces a new authorization gate in front of every MCP write/action dispatch. This section walks every existing V- and N- threat and records whether the gate (and its prompt-policy + UI companions) affects them. **No existing item regresses**; several get a small upgrade because the gate's audit trail is a new observability surface.

| Existing item | Regression risk | Assessment |
|---|---|---|
| `V-001` `new Function()` in chat flow | None | Gate code uses no `new Function()` / `eval`. The `tool_confirmation_gate.py` template renderer is a hand-written regex substituter, not a JS evaluator. The Svelte card uses static markup; the only JS in it is a fixed-purpose `postMessage`. |
| `V-002` Command injection via IPC handlers | None (slight upgrade) | The gate adds **no new IPC handlers**. Yes / No clicks reuse the existing `input:prompt:submit` postMessage channel, which is already covered by the renderer's same-origin check (`event.origin !== window.origin`). The card never accepts a tool name, args, or hash from the renderer's untrusted side — it only re-emits values the gate itself sent. Audit logging is in-process (stdlib log), no shell-out. |
| `V-003` `contextIsolation` on chat webviews | None | No webview prefs touched. |
| `V-004` `shell.openExternal` URL validation | None | The gate does no `shell.openExternal` work. |
| `V-005` ANSI sanitize-then-unsanitize | None | The card renders the gate's `summary` string and `args_preview` values verbatim with `{value}` Svelte interpolation, which HTML-escapes. The `summary_template` Mustache-lite renderer also returns plain strings; the only filters are `truncate` / `chars` / `join`. No HTML reflection of user input. |
| `V-006` Docker command injection via `serverId` | None | The gate does not invoke Docker; it runs purely inside the OWUI Python process. Tool args reach `call_mcp_tool_with_runtime_headers` only after gate dispatch authorizes — the args path itself is unchanged. |
| `V-007` Hardcoded API key with reversible XOR | None | Unrelated subsystem; gate doesn't read or write any runtime secret. |
| `V-008` Arbitrary env-variable injection via IPC | None | Gate adds no env-variable IPCs. |
| `V-009` Unsigned marketplace skill downloads | None | Unrelated. The gate sees skills as ordinary tool calls; if a skill exposes a destructive tool, it runs through the gate. |
| `V-010` Broad IPC surface without sender validation | None (slight upgrade) | New `chat:tool_confirmation` and `chat:tool_confirmation_rejected` events are server-to-client only — they piggyback on the existing `event_emitter` channel that already has the same trust posture as `chat:message:delta`, `files`, `embeds`, etc. The card's outbound path is the same `input:prompt:submit` postMessage that hand-typed replies use, and it travels through the existing same-origin check in `Chat.svelte`. The gate does NOT introduce a "click sends approval directly to the backend" handler. |
| `V-011` Marketplace skill -> XSS -> Host RCE | None | The chip escapes `summary` and `args_preview` via Svelte interpolation; no `{@html ...}` is used anywhere in `ToolConfirmationChip.svelte`. A malicious MCP that returns dangerous content cannot reach the host because the chip is rendered above the chat composer in the renderer, not in the privileged Electron shell. |
| `N-001` FTS regex ReDoS | None | Disjoint subsystem. |
| `N-002` Local bearer mismatch | None | Disjoint. |
| `N-003` Container runtime secrets via env | None | Gate does not touch Compose, secrets ingress, or the cache dir. |
| `N-004` Project-root plaintext twins | None | Disjoint. |
| `N-005` `CLOUDSMITH_API_KEY` packaged-build leak | None | Disjoint. |
| `N-006` Slack setup wizard `/tmp` debug log | None | Disjoint. |
| `N-007` Slack OAuth client_secret hardcoded | None | Slack now uses PKCE public-client OAuth and has no client-secret runtime flow for the gate to affect. |
| `N-008` Single-server OAuth HTTPS cert | None | Disjoint. |
| `N-009` Slack OAuth access token plaintext env | None | Disjoint. The gate reads tool args, not OAuth tokens. |
| `N-010` mcpo override `0.0.0.0` host bindings | None | Disjoint. |
| `N-011` `clean_full.sh` Slack OAuth artifact sweep | None | The gate's pending and approved stores are in-memory only — they do not persist to disk and therefore do not need a `clean_full.sh` entry. The audit log goes through the standard logging pipeline; if security ever wants persistent gate audit, `clean_full.sh` will need to be revisited at that point (tracked under N-012's "next proposed step"). |

**Other invariants preserved.** The gate runs on the OWUI Python side and emits server-sent events through the existing `event_emitter` infrastructure. Client-side consumption follows the same Svelte component pattern as `chat:message:files` / `chat:message:embeds`. There is no change to authentication, no change to OAuth scopes (the gate does not narrow what the MCP can technically do — only what the LLM is allowed to ask for without a fresh user confirmation), and no change to how secrets are delivered to the MCP runtime. A failure of the gate (e.g. registry file missing or malformed) falls back to the hardcoded fallback regex; a failure of the hardcoded fallback would still leave the prompt-policy soft layer in place. The gate's audit callback default emits to `logging` only; downstream sinks must opt in via `Gate(..., audit_log_fn=...)` when they want the events persisted.

### N-012 follow-up: scheduled-run scope binding & generic chip primitive (Phase 1+2+3 of the chip rework)

Three layered extensions land on top of the original gate without changing its core invariants:

- **Phase 3 — generic chip primitive.** The gate's renderable card was generalised from a tool-confirmation-specific shape to a `kind` / `prompt` / `options` / `allow_freeform` / `context` schema. The existing tool-confirmation chip becomes one `kind`; new `clarification` chips can carry any caller-defined option set with a stable id. The renderer POSTs to a single endpoint, `POST /api/v1/utils/chip/resolve`, with `option_id` as the canonical click vocabulary; the legacy `POST /api/v1/utils/tool-confirmation/resolve` wrapper was removed in the KISS pass since no in-tree client used it. The SSE event payload was strictly extended (no field removed) so any in-flight chip surfaced before the prune still resolves cleanly under the new `option_id` mapping (`approve` / `cancel` / `modify`). See the gate-level invariants documented in [`tests/test_tool_confirmation_gate.py`](../../tests/test_tool_confirmation_gate.py) (`Phase 3` section).
- **Phase 1 — pre-approved scope for scheduled runs.** The scheduling daemon stamps `chat.meta` on freshly-created sub-agent chats with `run_origin: "scheduled"`, `scheduled_task_id`, and `scheduled_approved_scope`. Inside a scheduled-run chat, the gate auto-dispatches in-scope destructive calls (audit `dispatched_scheduled_pre_approved`) and surfaces a three-option clarification chip for out-of-scope calls (`block` / `approve_once` / `widen_scope`). A `never_ask_again` option is intentionally NOT offered. The widen path delegates the actual `scheduling_update_task` call to the model so the audit trail flows through the scheduling MCP server's own logs. Trust boundary: `chat.meta` is only writable by the daemon's OWUI service token at chat creation time; no model-driven path can mutate it. See [`tool-confirmation.md`](tool-confirmation.md) ("scheduled-run scope binding" section) for the full model.
- **Phase 2 — pre-flight integration health check.** Both the skill ([`skills/scheduled-tasks/SKILL.md`](../../skills/scheduled-tasks/SKILL.md) "Pre-flight Checks" section) and the daemon executor ([`src/core-mcp-rust/crates/scheduling-server/src/preflight.rs`](../../src/core-mcp-rust/crates/scheduling-server/src/preflight.rs)) verify that every `tool_server_id` referenced by a scheduled task is installed and enabled before the run starts. Mismatches surface as `last_run_status: "missing_integration"` with a descriptive `last_run_error` listing each offending integration. Fail-closed semantics: a filesystem error on the configs-dir read is recorded as a missing-integration too.

**Threat model deltas** (delta-only; full table in [`tool-confirmation.md`](tool-confirmation.md)):

| Threat | Mitigation added |
|--------|------------------|
| Out-of-scope tool call inside an unattended scheduled run | Three-option clarification chip; user picks block / approve-once / widen. |
| Scheduled task references an integration that gets removed later | Executor preflight aborts the run with `missing_integration` instead of producing a silent failure. |
| Renderer injects a forged `option_id` to bypass the security-bounded choices | Gate validates option_id against the chip's declared options; unknown ids audit `gate_bypass_attempted` and resolve to `None`. |
| Model spoofs `chat.meta` via synthesized user-message content | Reader only consults `Chats.get_chat_by_id`, never message content. Pinned by [`tests/test_scheduled_run_scope.py::test_forged_user_message_cannot_supply_chat_meta_to_bypass_gate`](../../tests/test_scheduled_run_scope.py). |

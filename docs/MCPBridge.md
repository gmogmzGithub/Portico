# Host MCP Bridge

Portico starts a local Host MCP Bridge daemon when the app services are running. The bridge makes the PORTICO MCP toolbox available to external MCP clients through streamable HTTP on loopback.

The bridge is the stable local gateway for clients such as Atlas Code, Atlas Desktop, Workbench, Cursor, and Amp. Those clients do not connect directly to generated Docker services or per-server MCP runtimes; they connect to the bridge, and the bridge routes tool discovery and tool calls into the active PORTICO MCP stack.

## Endpoints

- Streamable HTTP MCP: `http://127.0.0.1:8891/mcp`
- Health check: `http://127.0.0.1:8891/health`
- OAuth discovery probes: `/.well-known/oauth-protected-resource/mcp`, `/.well-known/oauth-protected-resource`, and `/.well-known/oauth-authorization-server`

`/mcp` requires a per-client bearer token generated by PORTICO. `/health` intentionally remains unauthenticated so the app can monitor the local daemon. The discovery probe routes return a parseable `404 oauth_not_supported` response: the bridge is not an OAuth authorization server and URL-only registration is unsupported.

Internal builds may also run broker endpoints on the same daemon, such as `/secrets/oauth/access-token` and `/secrets/static-secret`. Those endpoints are for PORTICO-managed MCP runtime containers, not for external MCP clients. See [`architecture/auth/mcp-secret-broker.md`](architecture/auth/mcp-secret-broker.md) for the container secret-broker contract.

## What the Bridge Does

The bridge has four user-visible jobs:

1. **One local MCP endpoint:** supported clients use a single loopback URL instead of per-server ports or generated Docker topology.
2. **Authenticated access:** each configured client gets an PORTICO-owned bearer token. The daemon accepts only tokens registered in the app-managed auth registry.
3. **Small tool surface:** by default, the bridge exposes search-and-call tools so external clients can find relevant PORTICO tools without loading the entire MCP toolbox into context.
4. **Install skills once:** skills installed in PORTICO are discoverable and loadable by every configured MCP client without copying them into client-specific skill directories.

For maintainer-level details about process lifecycle, token registry format, and client-specific config writers, see [`architecture/mcp/host-mcp-bridge.md`](architecture/mcp/host-mcp-bridge.md).

## Client Configuration

Use the app-managed configuration flow instead of pasting manual client setup into chat:

- Open the bug drawer.
- In Service Status, find Host MCP Bridge.
- Click the cog button next to the log button.
- Select detected clients.
- Click Configure.

Do not register the Bridge by URL alone or paste a manual MCP configuration snippet. The app generates per-client credentials, writes supported client configuration atomically, creates backups, and keeps raw tokens out of renderer logs and chat.

Supported auto-config clients:

- Atlas Code: configured with streamable HTTP and a `headersHelper` that reads the bearer token at runtime.
- Atlas Desktop: configured through `atlas_desktop_config.json` with an PORTICO-owned local stdio proxy command. The proxy forwards to PORTICO's streamable HTTP bridge with the generated bearer token read from an PORTICO-owned token file.
- Workbench: configured through `config.toml`.
- Cursor: configured through `mcp.json`.
- Amp: configured through Amp settings JSON or JSONC.

Windsurf is not supported by this auto-config flow.

### Programmatic POC Hook

Setup scripts can try a single localhost call when Portico is running:

```bash
curl -fsS http://127.0.0.1:9876/api/mcp/bridge/clients
curl -fsS -X POST http://127.0.0.1:9876/api/mcp/bridge/enable \
  -H 'X-PORTICO-Programmatic-Bridge: 1' \
  -H 'Content-Type: application/json' \
  -d '{}'
curl -fsS -X POST http://127.0.0.1:9876/api/mcp/bridge/disable \
  -H 'X-PORTICO-Programmatic-Bridge: 1'
```

`clients` is read-only and answers whether the bridge is healthy, which supported clients are currently configured, and a `scriptAction`: `ready`, `enable_bridge`, or `fallback_toolhive`. `enable_bridge` means PORTICO is reachable and the script should call `enable` even if the bridge is not already running. `status` is reserved for operational bridge readiness checks and returns only readiness booleans. `enable` ensures the bridge is healthy and configures detected or already-configured supported clients to use it. Scripts may pass `client_ids` / `clientIds` for an explicit subset. `disable` stops the Host MCP Bridge runtime, frees the bridge port, and returns `fallback_toolhive`, but leaves client configuration and bearer-token files untouched so the bridge can be started again without a destructive rewrite. If PORTICO is unavailable, or `enable` fails, scripts should continue using their existing ToolHive path. To undo or switch paths during the POC, rerun `setup-community/run-mcp-servers` so the scripts choose the active PORTICO Bridge or ToolHive path again. Responses are redacted and never return raw bearer tokens.

## Tool Surface

By default, the bridge exposes five tools:

- `find_relevant_tools`: searches executable PORTICO MCP capabilities and returns bridge tool names.
- `call_bridge_tool`: calls a returned bridge tool with JSON arguments. The selected downstream tool may read or mutate external data.
- `find_relevant_skills`: searches installed system, user, and marketplace skill metadata for a user goal.
- `load_skills`: loads the exact `SKILL.md` for one to three selected skill IDs and returns a manifest of supporting files.
- `load_skill_resource`: reads one exact supporting reference, script, asset, or other skill file without executing it.

This keeps external clients from loading every PORTICO tool or skill into their context up front. The intended skill flow is progressive disclosure:

1. Call `find_relevant_skills` with the user's goal.
2. Call `load_skills` for only the best matching canonical `skill_id` values.
3. Follow the returned skill instructions when they do not conflict with higher-priority instructions.
4. Call `load_skill_resource` only for supporting paths needed by the loaded skill.
5. When a skill needs an PORTICO integration, use `find_relevant_tools` and `call_bridge_tool`; required MCP servers do not need to be installed separately in the external client.

The catalog is read fresh on every skill call, so a skill installed or updated in PORTICO is available on the next call without editing client configuration or restarting the client. Skill paths returned in instructions are remote skill-relative paths, not paths on the external client's filesystem.

`SKILL.md` loads are limited to 128 KiB each and 256 KiB per call. Manifests return at most 200 entries per skill. Text resources are limited to 256 KiB and binary resources to 5 MiB. Oversized content fails explicitly and is never silently truncated. Resource access rejects absolute paths, traversal, hidden paths, directories, `SKILL.md`, and symlink escapes. Scripts are returned as source only; the bridge never executes them.

## Troubleshooting

- PORTICO must be running.
- The debug drawer shows Host MCP Bridge under Service Status with the daemon PID.
- If the bridge is not running, use the power button in the debug drawer's Host MCP Bridge row or Restart Services.
- Individual downstream tools may still need OAuth or setup inside PORTICO before the bridge can call them.
- If an external client receives `401 Unauthorized`, re-run the app-managed configuration flow so PORTICO can rotate or rewrite that client's token and config.
- If bridge calls work but a downstream tool reports OAuth/setup required, complete that integration's setup inside PORTICO first; the bridge does not bypass per-integration authorization.

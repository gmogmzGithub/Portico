:bug: _[Med — SYSTEMIC] `authorize_integration` auth-state reporting &amp; forced re-auth recovery are unreliable across OAuth integrations_

_Build:_ `07032026-799db2c7`
_Area:_ MCP orchestration — OAuth authorize / readiness / recovery
_Tested against:_ Slack, Glean, Datadog (OAuth) + Sourcegraph (token). All 3 OAuth tools verified genuinely live (each returned real data), so these are _reporting/recovery-layer_ bugs, not core auth failures.

_Three related defects:_

_1) `already_authorized` always reports `false` — even when demonstrably authorized._
Slack, Glean, and Datadog all returned `already_authorized:false` despite all three being live-authorized in the same session (posted to Slack, searched Glean, queried Datadog monitors). This is the field a caller uses to decide whether to prompt the user, so it drives unnecessary re-auth prompts. Confirmed on 3/3 OAuth integrations → systemic.

_2) `force_auth=true` is a no-op when a token already exists._
Docs: `force_auth=true` should "force a fresh OAuth flow instead of reusing cached readiness/tokens." Called on Datadog → returned in ~4.2s with `success/tool_ready/"OAuth done"`, _no modal, no user interaction, no fresh flow_ — identical to the non-forced call. This is the documented recovery path for expired/invalid tokens (the system prompt tells agents to use `force_auth=true` after 401s), so if it silently reuses a stale token the recovery path is broken.

Earlier this session, Slack's `authorize` reported `tool_ready`/`success`/"OAuth done" while the actual Slack tool still 401'd until manual OAuth completion. The readiness claim is optimistic — based on token presence / process health, not an authenticated round-trip.

_Combined failure mode:_ tool 401s → agent calls `force_auth=true` (per docs) → gets "tool_ready!" (Bug 2) → tool 401s again → loop. Bugs 1 &amp; 2 are the mechanics; Bug 3 is the user-impacting symptom.

_Suggested fixes:_
• Make `already_authorized` reflect actual prior token state.
• Make `force_auth=true` actually invalidate cached tokens/readiness and force a fresh flow.
• Back `tool_ready` with a lightweight authenticated probe, or clearly separate "process ready" from "auth verified."
_Verified correct:_ token vs OAuth guardrail works — `authorize(sourcegraph)` correctly refused with `NOT_OAUTH_SERVER` and routed to guided setup. Core auth is functional; only the reporting/recovery layer is unreliable. *Sent using* @U0B8HGV43RS

Major PORTICO-170 Agent VM lacks disk quota and PID cap PORTICO-170 !94
Reported by David Appelbaum · 2026-07-04 19:03 UTC
:bug: _[Med] Agent VM resource isolation gaps: no per-VM disk quota + unbounded PIDs (memory/CPU are fine)_

_Build:_ `07032026-799db2c7`
_Area:_ Agent VM cgroup / resource limits

_What's enforced correctly (verified):_
• Memory: `memory.max`=1 GiB + `swap.max`=1 GiB → process OOM-killed at ~2 GiB (exit 137, `oom_kill` counter incremented). :white_check_mark:
• CPU: `cpu.max`=200000/100000 → capped at 2 cores. :white_check_mark:
_Gaps found:_

_1) No per-VM `/work` disk quota (higher severity)._ `/work` is the shared host virtiofs mount (461 G, already _86% full_). A VM wrote a 200 MB file instantly at ~900 MB/s with no cap; nothing limits total usage. Blast radius is shared — a runaway loop or long session can fill the host disk and impact EVERY chat plus the host itself.
- _Compounding:_ MCP overflow files auto-accumulate in `/work/.mcp-overflow/` (observed repeatedly this session — Glean/Sourcegraph results spilled 8–15 KB files, and a 12 MB `read_file` spilled a 13 MB file). They persist in the user's workspace and count against the same uncapped host disk.

_2) `pids.max = max` (unbounded)._ No cgroup PID cap — safely spawned 400 processes with no limit hit (`pids.current` reached 404). Only backstop against a fork bomb is the memory cap. Cheap to add a ceiling for defense-in-depth.

_3) Minor: `nproc` reports 10 but CPU is capped at 2 cores._ Libraries/tools that size thread/worker pools off `nproc` will over-subscribe 5×.

_Suggested fixes:_
• Add a per-VM/per-chat disk quota (or a dedicated volume) so `/work` writes can't exhaust the shared host disk; garbage-collect `.mcp-overflow/` on VM teardown and/or store spill outside the user mount.
• Set a reasonable `pids.max` ceiling.
• Constrain `nproc`/cpuset visibility to match the 2-core `cpu.max`. *Sent using* @U0B8HGV43RS

_Area:_ Reasoning/think-tag parsing — `patches/backend/open_webui/utils/middleware.py` + `custom_callbacks.py`
_Status:_ Root cause CONFIRMED via code trace + empirical repro (not a hypothesis).

_Symptom:_ A turn displays "Thought for N seconds" and an empty or truncated response body, even though a full answer was generated. Adjacent turns leak literal closing-think-tag fragments into the visible message text.

_Confirmed root cause (code-traced in `portico/portico`):_
There are TWO independent, naive string-matching reasoning parsers:
• _Display side_ — `middleware.py` `tag_content_handler` (~L2225) + `DEFAULT_REASONING_TAGS` (~L128, includes `&lt;think&gt;`, `&lt;thinking&gt;`, `&lt;reason&gt;`, `&lt;thought&gt;`, …). It scans _streamed answer text_ for these tags. A stray/model-emitted opening think-tag in the answer opens a phantom "reasoning" block; everything after it is rendered inside the collapsible "Thinking…/Thought for N seconds" panel and disappears from the answer body. Duration (the "Thought for Ns" label) is finalized ~L2317–2342.
• _Request-shaping side_ — `custom_callbacks.py` `extract_reasoning_from_text` (L138) uses `re.sub(r'&lt;think&gt;.*?&lt;/think&gt;\s*', '', text, DOTALL)` (L147). A stray tag pair in the answer excises the content between them (non-greedy + DOTALL).
_Empirical repro:_ Ran both regexes against answer text that contains literal think tokens (e.g. a bug report that discusses think tags). Result: content between/after the tags is stripped or moved into the reasoning block, leaving an empty/truncated visible answer.

_Trigger:_ Any assistant answer whose text contains reasoning-tag-like strings (think/thinking/reason/thought tags) — e.g. answers discussing LLM reasoning, pasted model output, or code containing those tokens.

_Meta note / live repro:_ This fired earlier in THIS session — when I was drafting bug reports that literally contained think tags, the UI showed "Thought for 24s" with no body, and stray closing-tag fragments leaked into nearby messages. The bug is self-triggering whenever the assistant writes about reasoning tags.

_Impact:_ Silent, total loss of the visible answer with no error indicator — appears as a normal completed turn. Deterministically triggerable. High severity (data loss + no recovery signal).

_Suggested fix:_ Only collapse reasoning that the model actually emitted via reasoning stream fields (`reasoning_content`/`reasoning`/`thinking`, already handled ~L2675) — NOT literal tags appearing in normal answer `content`. Neutralize/escape reasoning-tag-like substrings in answer text before rendering, and require a matched, model-originated open/close pair rather than any inline occurrence.
